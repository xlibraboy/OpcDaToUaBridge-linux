# Taste
- Delegates git commit and push of completed work to the agent; wants changes committed and pushed to origin (main) when work is finished (explicitly asked to "commit and push" after a task was done on multiple separate occasions, including again after this task). Confidence: 0.9
- Prefers Docker as the source of truth for toolchains/SDK versions and for running the app — when a project has a Dockerfile, read it to determine the SDK/base image and build/run in Docker rather than relying on host-installed tooling (e.g. "for .net sdk please see on docker"; again explicitly asked "please run with docker" instead of host `dotnet run`). Confidence: 0.9
- Wants runtime/service state checked via Docker — when asked whether a service is running, inspects containers (`docker ps -a`, including stopped ones) rather than host processes, because the user runs services as containers ("please check on the docker"). Confidence: 0.7
- Wants answers scoped strictly to the component/service asked about; corrects the agent when it answers about a different one (e.g. clarified "OPC UA sim server only" after the agent reported on the DA simulator). Confidence: 0.5
- Wants UI/config actions to be idempotent: when a button (e.g. "Use" on a discovered OPC UA server) adds something to a configuration list, it should auto-add only if not already present, and otherwise just select/use the existing entry without creating duplicates. Confidence: 0.6
- Wants distinct config entries to never overwrite each other: entities that share a common key (e.g. two OPC UA servers on the same host) must get unique identities (Source ID derived from host+port), so adding the second one never silently clobbers the first. Confidence: 0.8
- Wants the form-fill "Use" flow to NOT auto-save: it should populate the form as a new, unsaved source with an editable Source ID, and require the user to click Save — so the user keeps full control over the Source ID before anything is created. Confidence: 0.9
- Wants selectors/indicators of "selected" config entities (e.g. the Selected source dropdown) to reflect only persisted state — while editing a new, unsaved entry the selector should be empty rather than showing the previously selected name; it should only populate after the entry is actually saved. Confidence: 0.6
- Wants the identifier that keys a config entity to its mappings (e.g. Source ID used in node IDs) to remain locked/uneditable once the entity is saved, since renaming it would break the mappings — the value should be set at creation time instead. Confidence: 0.7
- Wants timestamps displayed on HMI screens to include millisecond precision (formatted like `yyyy-MM-dd HH:mm:ss.fff`); explicitly asked to show ms on the faceplate timestamp. Confidence: 0.6
- Reports UI issues by attaching screenshots (often directing attention to a specific element, e.g. "focus on 'DECIMALS'") and expects the agent to inspect the visual state in the image to diagnose rather than just re-asserting the code is correct. Confidence: 0.7
- Runs GUI apps in this project (HMI and its designer) as Docker containers forwarded to the host X11 display using a consistent run recipe — `--network host`, `-e DISPLAY=:0`, XAUTHORITY, XDG_CACHE_HOME/XDG_RUNTIME_DIR, `/tmp/.X11-unix` mount, and `--user "$(id -u):$(id -g)"` — reusing the same setup for each GUI app rather than inventing a new one. Confidence: 0.6
- Wants supporting infrastructure/services (e.g., InfluxDB) deployed as Docker containers with initial credentials/org/bucket/token provisioned, so the app can connect to them — not installed on the host ("can you install to docker? so i can connect later on with url, org, bucket, token"). Confidence: 0.8
- Wants UI elements sized so their text is fully visible — treats clipped/truncated text (e.g. an input whose placeholder "off (full precision)" is cut off because the field is too narrow) as a bug to polish, expecting the width to be enlarged to fit the content. Confidence: 0.5
- Prefers discovery/scan-based configuration for external services over typing full URLs: asked for an InfluxDB "Scan" button (mirroring the existing OPC UA discover pattern) so only an IP/host needs to be entered and the app probes the server and auto-fills the URL. Confidence: 0.5
- Prefers type-derived defaults over arbitrary fixed types for numeric ranges — when asked about min/max for trend Y-axis, explicitly said "Min Max type are based of the tags type (not fiz used double)", meaning use the natural range of the tag's DataType (e.g. 0–65535 for UInt16, 0–1 for Boolean) rather than a generic double range. Confidence: 0.8
- Prefers a "dashboard sets, designer consumes" workflow for tag metadata like Unit — the web dashboard is where the user types the engineering unit name per tag (stored in TagMapping), and the HMI designer reads it from the tag cache; the designer may offer a manual override but the dashboard is the primary entry point ("we type from web dashboard, so from designer can get the unit name from dashboard"). Confidence: 0.8
- Prefers tag display properties (unit, label) to be configured in the web dashboard, not the HMI designer — the dashboard faceplate (Tags → Maps → tag → Setup tab) is the natural place for tag-level metadata entry; the designer consumes it. Confidence: 0.7
